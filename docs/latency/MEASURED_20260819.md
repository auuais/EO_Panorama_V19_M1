# Measured timing, 2026-08-19

Build `67955bc` (`V19TimingProbe`), routed WNS +0.018 / WHS +0.006 /
WPWS +0.050, archived at `builds/bit_archive/20260819_timingprobe_67955bc/`.

The probe measures intervals in fabric because an ILA window is 8.8 us and
carries no timestamps; see `src/V19TimingProbe.v`. It is calibrated against
known intervals in `sim/tb_V19TimingProbe.v` (8/8 checks pass).

---

## 0. Optical cross-check, and what it overturned

Every rate below was re-measured on the far side of the SDI link with a
different instrument and a different mechanism -- grabbing at ~60 fps and
counting distinct frames by exact hash (`scripts/measure_output_rate.py`).

| mode | electrical (fabric counter) | optical (distinct frames) | |
|---|---:|---:|---|
| IR single | 30.01 | **29.78 / 29.95** | agrees |
| EO panorama | 15.03 | **14.73** | agrees |
| IR panorama | 15.03 | **14.98** | agrees |
| EO single | 29.75 | **14.81 / 15.14** | **DISAGREES** |

The grabber is not the confound it might have been.  IR single returns repeat
runs of *exactly 2* at a 59.9 fps grab rate, 240 times in a row -- the card
resolves 30 distinct frames per second perfectly.  Lower resolution and MJPEG
change nothing, so link bandwidth is not a limit either.

### The EO single disagreement is real, and it is the cameras

EO single commits 29.75 output frames per second but the picture only changes
~15 times per second, with repeat runs of 4.  Measured on **all six** EO
cameras: 14.97, 14.97, 14.81, 14.97, 15.14, 14.97.  Uniform.

Copies cannot outrun descriptors -- a copy is triggered by one -- so the FPGA
is receiving and publishing ~30 complete camera frames per second while only
15 of them carry a different image.  **The EO cameras transmit each image
twice over BT.1120.**  Each distinct EO image is held for 66.8 ms; each IR
image for 33.3 ms.

*Deduced, not measured at the camera interface.*  It is consistent with every
measurement taken and with the IR cameras behaving differently on the same
output path, but confirming it belongs in the camera configuration, which is
far quicker to check there than from the FPGA.

**Consequence:** EO effective content rate is 15 fps at source.  No FPGA work
makes EO single show 30 distinct frames per second.

\* the IR panorama input figure is the one number here not to trust: it reads

## 2. Read the counted column, not the interval column

`per_commit` reports the LAST measured interval. A pipeline that has stopped
committing keeps reporting whatever it managed most recently, so IR panorama
read as a healthy 33.3 ms while committing nothing at all. Counting commits
over a wall-clock gap (`scripts/measure_commit_rate.sh`) cannot be fooled that
way, and it is what the table above uses.

The same trap caught EO single in the first run, which reported 15.00 fps from
a stale interval captured seconds after programming. Counted over 64 s it is
29.75. **Always cross-check the two.**

## 3. Full latency

The probe measures from a frame becoming available (its completion descriptor)
to the output frame built from it being committed. Two further terms complete
the picture, and both are ranges rather than fixed values:

* a row's **age at descriptor time** - the first row of a frame was captured
  a frame period before that frame completed, the last row essentially none;
* its **scan-out position** - where the row sits in the output raster.

Each is 0 to 33.3 ms, averaging 16.7 ms.

| mode | min | typical | max |
|---|---:|---:|---:|
| EO single | 16.4 ms | **49.8 ms** | 83.1 ms |
| EO panorama | 41.1 ms | **74.5 ms** | 107.7 ms |
| IR single | 50.1 ms | **83.5 ms** | 116.7 ms |
| IR panorama | 45.0 ms | **78.3 ms** | 111.7 ms |

Camera sensor and ISP delay is excluded throughout - vendor specification.

## 4. What this corrects in the derived analysis

The first version of the deck derived 100 / 117 / 100 ms typical for EO single,
EO panorama and IR single. Measurement shows the EO figures were **too
pessimistic by 30-50 ms**, because the derivation assumed the render stage
occupies a full frame period and the commit adds a further half frame. EO
single's copy actually completes 10.1 ms after the descriptor. IR single came
out close (83.5 measured against 100 derived).

## 5. Why the panorama modes publish at 15 fps, and why EO panorama then
discards half its input

### 5.1 It is not render throughput

Copy occupancy, sampled without a trigger bias (a capture armed ON
`copy_active` cannot sample the idle half, and reported a misleading 84%):

| mode | copy duty | publish cadence | => copy duration |
|---|---:|---:|---:|
| EO single | 25.0% | 33.6 ms | **~8.4 ms** |
| EO panorama | 37.5% | 66.5 ms | **~24.9 ms** |
| IR panorama | 40.0% | 66.6 ms | **~26.6 ms** |

EO single's ~8.4 ms agrees with its independently measured 10.1 ms
descriptor-to-copy-done, which is a useful cross-check on both.

**In every mode the render fits inside a 33.3 ms frame period.** Throughput is
not the limit.

### 5.2 It is the two-bank output framebuffer

    copy_bank_available = !pending_valid && (!frame_valid || (wr_bank != rd_bank))

One output bank is being scanned, the other is under construction. A finished
frame sets `pending_valid` and waits for the next output frame edge to be
committed; **no new copy may start until then.** So the sequence per published
frame is: start -> render -> wait for the frame edge -> commit -> start again.

That still allows 30 fps *if* the render finishes before the next edge. The
panorama render takes ~25 ms of a 33.3 ms frame, leaving only ~8 ms of margin
for the delay between the frame edge and the copy actually starting. Exceed
that margin and the finish misses the edge, the commit waits a further whole
frame, and the loop settles stably at exactly half rate - which is what all
three cadence measurements show.

*Inference, not measurement:* the copy duration and the cadence are measured
and the bank rule is read from the RTL, but the copy-start delay itself has
not been timed. Confirming it needs the probe extended to timestamp
`copy_start_accept` against `frame_edge`.

### 5.3 The discarded EO input costs nothing - correction

Source banks are released on `v19_consumer_done`, which in panorama is
`v19_copy_frame_done`. So source banks recycle once per published frame, and
at 15 published frames per second the writers are admitted 15 times per second
while 30 rasters arrive. The surplus is discarded at `frame_start`.

**Earlier this document said half the cameras' output is discarded. That
is true of rasters and false of content.** The optical measurement in section
0 shows the EO cameras only produce 15 distinct images per second; the
discarded rasters are the duplicates. EO panorama therefore displays every
distinct EO image the cameras produce, and its 15 fps output matches the
source exactly. Nothing is lost.

This does not apply to IR panorama - see 5.5.

### 5.4 What would fix it

1. **A third output bank.** Removes the coupling outright: a copy can start
   while the previous frame waits to be committed, so the ~8 ms start margin
   stops mattering. Costs one more output frame of memory.
2. **Start the copy earlier.** Reduce the delay between the output frame edge
   and copy start - for EO panorama that means the six-camera lease being
   ready sooner, which is a phase-alignment problem between capture and output.
3. **Shorten the render.** ~25 ms against a 33.3 ms budget has little slack;
   DDR headroom (the single-command launcher, the 256-of-384-bit payload) would
   widen it.
4. **Release source banks on replay completion rather than on output
   completion**, so capture admission is decoupled from display rate even if
   the display stays at 15.

Items 1 and 4 are independent. For **IR panorama** item 1 is the one that
matters, because there the lost frames are real content.

### 5.5 IR panorama is the mode that actually loses frames

The IR cameras genuinely produce 30 distinct images per second - IR single
displays all 30 of them through the same output stage, measured optically at
29.78 and 29.95. IR panorama publishes only 15.03, so **half the IR content
never reaches the display.**

Its cause is not source-bank recycling: direct ingress has no DDR source banks
at all. It is the two-bank output framebuffer of 5.2. The render takes
~26.6 ms of a 33.3 ms frame, leaving ~7 ms for the copy to start after the
frame edge; miss that and the commit waits a whole further frame. IR single,
whose render takes only a few ms, has margin to spare and holds 30 fps on the
identical output path - which is what makes the diagnosis specific rather than
speculative.

A third output bank (5.4 item 1) is the direct fix, and IR panorama is where
it would buy real frames rather than duplicates.

## 6. IR panorama works from boot and dies on a mode switch

Measured, in this order:

| state | commits/s |
|---|---:|
| after a mode switch into 0x14 | **0.00** (zero in 70 s) |
| 1-point NUC on all six IR cameras, still in 0x14 | **0.00** (zero in 72 s) |
| switch to IR single, NUC all six, switch back | **0.00** (zero in 64 s) |
| **straight after reprogramming the part** | **15.03** |

The counter is the evidence: it froze at exactly 1569 across two separate
60-second windows, ran freely during the IR single interlude (1569 -> 2122),
and froze again the instant the mode returned to 0x14. A capture armed on
`copy_active` also never triggered in 10 s.

So mode 0x14 is not broken - it is broken **by mode switching**, and no camera
-side recovery reaches it. This matches the known issue the
`codex/ir-ddr-buffer` fork works around with DDR input buffering and rejoin
guards; the main branch has neither.

Practical consequence for anyone measuring or demonstrating this mode on the
main branch: **program the part and go straight to 0x14.** Any excursion
through another mode requires reprogramming to recover.

Not confirmed visually - the USB3 capture card was held exclusively by another
application throughout (it enumerates as "USB3 Video", status OK, but cannot be
opened). The electrical evidence is independent of the display path.

## 7. Caveat on the EO panorama latency

The probe freezes the input timestamp at copy start, which for EO single is
exactly the frame being copied. In panorama the copy consumes a *leased set*
chosen by common epoch, whose frames can be older than the most recent
camera-0 descriptor. So 41.1 ms is a lower bound on EO panorama latency;
the displayed set may be older than the frame the probe timed from.

Closing this needs the lease epoch carried alongside the timestamp, which is a
further build.
